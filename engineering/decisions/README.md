# 架构决策记录（ADR）

> 用途：为具有长期跨模块影响的工程决策提供轻量记录方式。  
> 权威来源：已接受 ADR、相关源码/测试以及 [系统架构](../architecture.md)。  
> 更新触发：ADR 状态、模板、决策治理或替代关系发生变化。

## 何时创建 ADR

适合记录：

- 影响多个运行时或客户端的 contract；
- 改变持久化、同步、queue、deployment 或安全边界；
- 引入长期维护成本或迁移计划；
- 存在多个合理方案，需要保留取舍理由；
- 替代已有架构决策。

不需要记录：

- 局部实现细节；
- 容易撤销且不影响兼容性的重构；
- 已由公开标准或现有模块规则明确决定的事项；
- 单纯依赖升级，除非同时改变架构或兼容性。

## 文件与状态

文件名使用 `NNNN-short-title.md`，编号递增。状态为：

- `Proposed`：正在讨论，尚不能作为实施依据。
- `Accepted`：已同意并作为当前决策。
- `Superseded`：已被后续 ADR 替代，必须链接替代文件。

ADR 不保存秘密、凭据或只存在于外部聊天中的必要上下文。

## 模板

```markdown
# ADR-NNNN：决策标题

- 状态：Proposed | Accepted | Superseded
- 日期：YYYY-MM-DD
- 决策者：相关维护者或团队
- 替代：无，或被替代 ADR 的相对链接

## 背景

说明问题、约束和必须做出决策的原因。

## 决策

说明选定方案及其适用范围。

## 备选方案

列出实际评估过的方案及未采用原因。

## 影响

记录正面影响、成本、迁移要求和后续维护责任。

## 验证

列出证明决策有效的测试、指标或人工检查。
```

## 维护规则

- 接受 ADR 前，确认 [信息唯一归属](../maintenance-guide.md#信息唯一归属) 没有被破坏。
- 实施完成后，将相关工程文档链接到 ADR，而不是复制完整决策历史。
- 替代决策时保留旧文件，将状态改为 `Superseded` 并建立双向链接。
- 决策不再适用且没有替代方案时，在影响章节解释原因，不直接删除历史。
